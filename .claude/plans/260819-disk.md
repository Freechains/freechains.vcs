# 260819-disk

- alternatives to shrink `.git/states/` beyond prune
- prune (260818) caps at O(keep*N); this asks for a
  smaller CONSTANT or a better ASYMPTOTE
- not scheduled: a design survey, pick later

# Root cause

- one snapshot per commit, each a FULL serialize of `G`
  (~0.5*N KB), so total O(N^2)
- but consecutive states differ by O(1) AMORTIZED: a commit
  adds one action + reps deltas; each action matures once
  (12h refund, 24h consolidate), so total real change over
  the whole chain is O(N), not O(N^2)
- => snapshots are ~99% redundant; every idea below is a way
  to stop paying for that redundancy

# 1. Lua -> database (sqlite)

- store `G` in one SQLite file, not per-commit `.lua`
- alone it does NOT fix O(N^2): the cost is snapshotting the
  WHOLE state per commit, which a DB still pays unless the
  SCHEMA is versioned/delta (temporal tables: a validity
  range per row, MVCC you build yourself)
- real wins are operational: one file, indexed queries
  (`reps`, membership) instead of parsing a growing table,
  no O(N) load per command
- combine with a delta schema to also beat the asymptote
- see existing `sqlite.md`
- verdict: good for query cost + one-file tidiness; needs a
  versioned schema to help disk; medium effort

# 2. Spaced snapshots + recompute

- keep a snapshot every K commits (checkpoints); to read
  state at C, load nearest ancestor checkpoint, replay to C
- disk: O(N/K) checkpoints * O(N) each = O(N^2/K) -- still
  quadratic for fixed K, just /K smaller
- to go sub-quadratic, space GEOMETRICALLY (depths
  1,2,4,8,...): O(log N) checkpoints on any path, replay
  bounded by the gap
- read cost: replay up to K (or one gap) commits -- bounded
- this is E0 (recompute-on-miss) but SAFE now: prune already
  refuses forks below the boundary, so recompute only ever
  runs inside the kept window (no pre-validation DoS)
- orthogonal to prune: prune caps the range, spacing thins
  WITHIN it. Composes.
- verdict: real sub-quadratic, classic checkpoint/replay;
  cost is replay-on-read complexity; medium effort

# 3. Diff-based store (delta chain)

- store each snapshot as a delta vs its parent snapshot
- since amortized real change is O(1)/commit, the delta
  chain is O(N) TOTAL (not O(N^2))
- caveat: `advance()` can mature MANY entries at one commit
  (a 12h/24h boundary refunds a batch) -> that commit's
  delta is big, but each entry matures once, so the SUM
  stays O(N)
- read state at C: apply deltas from the nearest full base
  (so it also wants periodic full bases -- item 2 again)
- this is exactly a Mercurial revlog: inline deltas +
  periodic snapshots, built for this shape
- verdict: best asymptote (O(N) storage), but hand-rolling
  a delta format + base cadence is real work

# 4. State versioned in git (reuse the packfile)

- keep ONE state file; commit a new version each action into
  a git repo (a parallel `refs/state/*`, or a second repo);
  on sync, checkout the version at `oct`
- git ALREADY gives what items 2+3 hand-roll:
    - zlib on every blob ("auto zip"): ~5-10x even with no
      delta
    - packfile DELTA between near-identical versions after
      `gc`: the O(N) delta chain, for free
- so packed disk ~ O(N), reusing code we already run (gc is
  stage 1 of sweep)
- catches:
    - LOOSE objects are full-blob-per-commit until packed ->
      O(N^2) transient; must `gc` regularly (already do)
    - no need for git to MERGE state: state is DETERMINISTIC
      from the DAG, so just WRITE the computed state and
      commit it; map freechains-cid -> state-commit, checkout
      by that. Storage only, not merge.
    - keep it OUT of the action tree (would change aids)
- Mercurial revlog (item 3) is the same delta-log idea as a
  library instead of git
- verdict: highest leverage for least new code -- delegate
  redundancy to git's proven delta+zip; the work is the
  cid->state-version mapping and the checkout path

# Also: cheap, non-structural

- zlib each `.lua` snapshot in place: still O(N^2) but ~5-10x
  smaller constant, near-zero code. A stopgap under prune.

# Leaning

- shortlist: item 4 (git-stored state) for best power/effort,
  or item 3 (explicit delta chain) if we want no git coupling
- item 2 composes with either as the base-cadence knob
- item 1 is orthogonal (query cost), pursue via sqlite.md
- item 5 (zlib) as an immediate stopgap while deciding
- all compose with prune: prune bounds the RANGE, these
  shrink the per-snapshot COST
