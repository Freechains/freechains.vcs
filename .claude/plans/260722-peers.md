# Peers: git-backed peer list per chain

Goal:
make `sync send/recv` iterate over a stored peer list, so the URL
becomes optional.

## 1. Can git hold the peer list?

Yes.
Each chain is already a git repo, so peers live in its `.git/config`.
Two options:

| Option                    | Storage                     | Notes                                          |
|---------------------------|-----------------------------|------------------------------------------------|
| git remotes               | `remote.<n>.url`            | needs a name per peer, creates `refs/remotes/*` |
| **multivar config (pick)**| `freechains.peer` (--add)   | plain list, no naming, no extra refs            |

Chosen: `freechains.peer`, mirroring the existing `freechains.url`
(self-advertised URL set at `chains add`).

```
git -C <repo> config --add     freechains.peer <URL>
git -C <repo> config --get-all freechains.peer
git -C <repo> config --unset   freechains.peer <URL-regex>
```

Caveats:

- Git does *not* auto-iterate for us in the way we need:
    - `git fetch --all` fetches all remotes, but `recv` needs one
      `FETCH_HEAD` at a time to replay/merge sequentially.
    - `git push` has no all-remotes flag (only multiple `pushurl`,
      which loses per-peer error reporting).
- So iteration is a Lua loop in `sync.lua`; git only stores the list.
- The list is *local config*, not chain content: it is neither signed
  nor gossiped (see [peers.md](peers.md) for the reputation/gossip
  design).

## 2. Implicit URL in send/recv

Make the `remote` argument optional:

| Command                        | Behavior                                  |
|--------------------------------|-------------------------------------------|
| `chain #x sync send <url>`     | unchanged (single peer)                   |
| `chain #x sync send`           | loop `freechains.peer` list               |
| `chain #x sync recv <url>`     | unchanged                                 |
| `chain #x sync recv`           | loop list, one fetch+replay per peer      |

Rules:

- Empty list with no URL: error `chain sync : no peers`.
- One failing peer must not abort the loop:
    - print `peer <url> : <error>` to stderr, continue.
    - exit non-zero only if every peer failed.
- `recv` is sequential: state after peer `k` is the base for `k+1`,
  which the existing consensus/replay code already handles.
- `send` keeps the current hook dance (push rejected with
  `Freechains: OK`) per peer.

## 3. New commands

```
freechains chain <alias> peer add  <url>
freechains chain <alias> peer rem  <url>
freechains chain <alias> peer list
```

- `add`: reject duplicates and empty/invalid URL; store the URL raw
  (as typed), normalizing only at use time via `URL(raw, alias)`.
- `rem`: error if absent.
- `list`: one URL per line, insertion order.
- `chains add <alias> clone <url>`: auto-add `<url>` as the first peer.

  (that is [peers.md](peers.md)).
- Parallel sync across peers.
- Named remotes / `git remote` integration.
