# Goal

- Recover from a hard fork by destroying local-only history
- New command: `freechains chain <alias> destroy <hash>`
    - `<hash>` is the FIRST post to remove, not the last to keep
- Local-only operation: no signing, no network, no reps

# Rationale

- After `sync send` fails with `hard fork`, the peer is unreachable
- Only escape: abandon local branch, take the settled one, repost
- Git backing is `git reset --hard <hash>^1`
- The rejected post is what the user knows: name it, not the fork point
- Chain state lives in-tree (`.freechains/state/*.lua`)
    - the reset restores it for free
    - no cache to rebuild
    - `reps` revert too: the destroyed posts never happened
    - so the repost needs no additional `reps`

# Names

- `destroy`: erases the named post and everything after it
    - irreversible and unrecoverable: the name must warn
- rejected `drop`: too mild for an unrecoverable operation
- rejected `reset`: `git reset` KEEPS its argument, we erase it
- rejected `revert`: `git revert` is additive (inverse commit)
- rejected `revert`: reads too close to `revoke`
- rejected `sync destroy`: sugar over four existing commands
- `destroy` vs `revoke`
    - `revoke` hides a payload for the community, and propagates
    - `revoke` is reversible, by `unrevoke`
    - `destroy` erases local history, and never leaves the peer

# Recovery flow

- `chain <alias> destroy <hash>`          -- destroy the rejected post on
- `chain <alias> sync recv <remote>`   -- take the settled branch
- `chain <alias> post ...`             -- repost on top
- `chain <alias> sync send <remote>`   -- back in sync

# Semantics

- `ERROR : chain destroy : invalid hash` covers all of
    - unknown hash, or not a commit
    - not an ancestor of `HEAD`, and not a beg
    - not a post/like/revoke (`state` and the genesis reject)
- a beg target deletes `refs/begs/beg-<hash>` and stops there
    - a beg is a post with nothing after it
    - `main` is left untouched
    - the only way to abandon a pending beg
- otherwise lands on `<hash>^1`
    - a post is always committed on top of a valid tip
    - so its parent is a `state` commit, a merge, or the genesis
    - no search, and a merge tip is reachable like any other
- destroying the first post empties the chain back to the genesis
- settled posts can be destroyed
    - hard-fork rule protects against remote reorder
    - it must not block a deliberate local escape
- prints each destroyed commit, one hash per line
    - skips `state` commits
- destroys `refs/begs/*` whose post is no longer reachable
    - same cleanup as the tail of `sync recv`

# Open

- should `destroy` refuse when the peer already holds the destroyed
  posts (they would return on the next `recv`)?
    - leaning no: `recv` merges them back by consensus anyway
- beg staleness uses `<beg>~2` (post + state shape)
    - relies on how `post --beg` builds the ref
    - breaks if the beg shape ever changes

# Won't do

- `sync destroy` one-shot recovery command
- `--replay` automatic repost of destroyed payloads
    - a repost is a new post: new hash, new time, re-signed
    - better explicit than hidden inside `destroy`
- `--dry` preview: `list dag` already shows the fork
- naming a `state` or merge commit: `list` never prints them,
  and `<hash>^1` already reaches a merge tip
