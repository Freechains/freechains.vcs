# Goal

- bound the per-action cost of freechains state
- measured at N=22k (11 MB state, 22.5k actions), one `post`:
    - git read/write: 0.07s (not the problem)
    - lua parse snapshot: 0.13s (O(N))
    - lua serialize snapshot: 0.47s (O(N), worst single term)
    - `advance()` discount scan: 0..3.6s (O(A*N), A = posts in 12h)
    - `ordered()` sort, twice: 0.10s
- disk: full snapshot per action -> O(N^2) loose, gc O(N^2) cumulative
- state never shrinks: 16.8k of 22.5k entries parked in `12-24`

# Attack model

- forks are FREE: no PoW, a branch may attach anywhere and
  recv must compute G at that floor to judge it
- entrenchment bounds REORDERING, not depth: an APPEND
  merge of an old branch is accepted at any depth and reads
  the floor state (260818-prune.md, "deep attach is not a
  hardfork"); bounding depth needs P2's explicit rule
- so the worst case: floors up to one window deep, repeatedly
- per-action snapshots are the STRONGEST design under attack:
  any floor is O(1) to read
- => retention must be WINDOW-aware, not count-aware:
  dense inside 7d (where every computable floor lives),
  decaying to nothing below the horizon
- re-validating the SAME hostile branch every recv is a
  separate cost: 260819-blacklist.md composes with any design

# Step 1: advance() one pass  [x] DONE

- was: inner loop over all actions per `00-12` entry, and
  `tot` recomputed per entry -- O(A*N)
- now: one sort, one walk; the authors acting AFTER an entry
  are a shrinking multiset (`cnt`), `cur`/`tot` kept LIVE
- LIVE matters: a refund mid-scan credits its author, and the
  entries after it must see it (the rescan did; a naive
  backwards precompute would not)
- verified: A/B vs old rules.lua on one genesis, every state
  blob byte-identical (discounts, begs, query-time earns)
- bench (synthetic, N=20k, 200 authors):
    - 00-12=500:  0.946s -> 0.038s (25x)
    - 00-12=2000: 5.452s -> 0.062s (88x)
- also: `ordered()` now runs once, shared by both scans

# Step 1b: maturity lists + windowed witness  [WITH STEP 3]

- goal: advance O(window) per call -- prerequisite of step
  3 (replay runs advance PER ACTION: a full sort + O(N)
  multiset init x K per command would cost seconds)
- SPLIT by maturity, sorted by time:
    - `12-24` list: the big bucket (16.8k of 22.5k), only
      the consolidation scan reads it; stays sorted FREE
      (discount matures in ascending time -> append);
      consolidation removes from the front
    - `00-12` list: tiny; binary insert at the tail (loser
      times bounded by the fork window, never before the
      settled prefix)
- WINDOWED witness: an action older than the OLDEST pending
  entry is in nobody's "acted after" set, so `cnt`/`cur`
  need only the last ~12h of actions, not all N: the full
  `ordered(G)` sort dies with it
- consolidated entries: tombstones in the hash only, in no
  list
- cost: lists serialize per snapshot, but hold only the
  PENDING window (hundreds), never tombstones
- MEASURED alone (26/08/31), then REVERTED: today one
  command = one load + one advance, so sort-at-load equals
  sort-in-advance -- zero gain standalone
    - first try serialized the lists: +30% disk, +7% post
      (12-24 is the unbounded earn queue, one cid dup per
      snapshot); fix = DERIVED index, stripped on write,
      rebuilt on read (one sort per load)
    - implement TOGETHER with step 3, derived-index form

# Step 1c: witness accounting  [REJECTED as prefix-sum]

- prefix-sum (`wit += reps_of(actor)` per action, O(1) per
  entry) REJECTED: counts an author per ACTION, manipulable
  by repeats; the rule counts each author ONCE
- exact once-per-author in O(log N), if ever needed:
  an action credits its author's reps to the entries born
  SINCE the author's previous action -- a contiguous birth
  range -> one range-add (Fenwick over birth order)
- step 1's multiset already does exact in O(N) per advance

- the real levers:
    - 2a: pack tombstones into a compact index (was option
      3): one dense structure instead of 16.8k tables;

        - intern authors: `G.keys = {pub1, ...}` (the 80 B

    - 2b: cheaper serializer for what stays (old step 4)

## 3a: append log of effect lines

- state file = sequence of effect lines, one action appends few
    - `act {cid,action,author,time}`
    - `reps {author,delta}`
    - `mature {cid,to}`
- every mutation of `G` emits its line (single mutation point)
- read = fold lines (assignment only, no `advance` replay)
- state at cid = fold of prefix; keep `cid -> offset`
- checkpoint snapshot every K lines, replay tail
- drops `refs/states/*`, `hash-object` per action, `sweep`
- expected: write O(1), disk O(N), no gc
- cons: the `act` lines duplicate the commits; every G write
  must funnel through the emit point; a new format to trust

## 3b: order + checkpoint + replay

- the commits ARE the log: persist only `order` (+ checkpoint
  G every K actions), state = replay the tail via ACTION.apply
- `order` is the one derived thing that must persist: it
  encodes fork resolutions (octopus/winner) already paid for
- no new format, no dual-write: the pipeline stays the single
  source of truth
- replay tail on LOCAL accepted history: skip SSH.verify
  (the per-commit process spawn, the dominant replay cost)
- after step 1, `advance` in the tail is cheap
- appending order is O(1): one 40-hex line per action, and
  replay along it is LINEAR (no meet/winner recursion)
- expected: tail K=100 in a few hundred ms, degrades with K
  not with N; serialize O(G) amortized to once per K
- checkpoints spaced by the WINDOW, not by count (see attack
  model): dense inside 7d, one below the horizon
- to verify first: sync recv reads G at ARBITRARY cids
  (octopus floors, beg parents) = replay of an order PREFIX
    - holds along ancestry; begs and loser branches need care

## 3c: periodic G only, no order  [REJECTED]

- checkpoints alone; order re-derived by climb/meet on demand
- works (recv already re-resolves forks structurally), but
  replay is DAG-recursive; 3b's order line is cheap enough
  to keep the replay linear

## 3d: BTC style, undo deltas  [REJECTED]

- BTC: one mutable state + per-block undo, rewind to floors
- ages badly here: undo depth = window depth on a busy chain,
  repeatedly, attacker-triggered (forks are free, see above)
- and G is one serialized file, not an in-place db: undo does
  not remove the serialize cost anyway
