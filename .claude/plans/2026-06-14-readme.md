## Verified mechanism

`sync send` does NOT push content. Per hook
`lua/freechains/hooks/pre-receive:42-47`, a push TRIGGERS the hub to
run `sync recv` back from the sender's `url`; the hub does the full
recv (consensus + merge) locally, then rejects the push with
`Freechains: OK` (treated as success by `sync.lua:13`).

Winner: `sync.lua:78-112` — the branch whose signers hold more summed
reputation at the common ancestor wins; tie -> smaller commit hash.

    ```
    $ freechains chain '#chat' post inline $'Alice was here\n' --sign=/tmp/alice
    a1b2c3d...
    $ freechains --root=/tmp/B/ chain '#chat' post inline $'Bob was here\n' --sign=/tmp/bob
    f4e5d6c...
    ```

    Both send their posts to the neutral hub `X`:

    ```
    $ freechains chain '#chat' sync send localhost:8331
    $ freechains --root=/tmp/B/ chain '#chat' sync send localhost:8331
    ```

    `X` resolves the divergence; since `Alice` holds more `reps`, her post is
    ordered first:

    ```
    $ freechains --root=/tmp/X/ chain '#chat' list order
    ...
    a1b2c3d...
    f4e5d6c...
    ```

    This is the core property of Freechains: **consensus via authoring
    reputation**, reached by every peer without any central authority.

## DAG merges: why forks look "open" (investigated 2026-07-23)

Observation: guide DAGs never show a merge/join node after a `sync`.

Root cause (this is BY DESIGN, not a rendering bug):
- `sync.lua:506-543` DOES create real Git merge commits on divergence
  (`git merge --no-commit` per loser commit, trailered
  `Freechains: merge`), plus a `Freechains: state` commit.
- `list dag` (`list.lua:37`) renders `V = G.order`, which is post/like
  ONLY.
- `backs()` (`common.lua:32`) recurses THROUGH `merge`/`state`
  commits and returns only post/like/revoke ancestors.

CORRECTION (measured 2026-07-28): the `Freechains: merge` commits never
reach `main`. They are built on a DETACHED head (`sync.lua:506`) and
thrown away by `checkout main` (`sync.lua:543`); only the final
`Freechains: state` merge (`sync.lua:593`) lands. On the guide hub,
`git log --merges` returns ONE commit, trailer `state`, and the chain
holds zero `merge` trailers. So `merge` is a kind the DAG never
contains today -- `backs` and `sync.lua`'s `commit` still handle it
defensively.
- So a visible JOIN appears only when an authored post/like has >=2
  `backs`, i.e. someone posts AFTER seeing both tips. No such post
  exists anywhere in the guide -> every fork stays visually open.

2.1 Consensus DAG (README ~398): correct as printed. `list dag` would
    output exactly that open fork; it just never shows that X
    reconciled.

2.2 Hard Forks: open forks also render correctly, but TWO wordings are
    imprecise:
    - "both sides converge to the same DAG": graph (nodes + authored
      `backs`) is identical on A and X, but `list dag` sequences/lays
      out via `G.order`, which DIFFERS per peer -> ASCII layout may
      differ. Prefer "the same underlying fork".
    - "permanent fork / cannot reconcile": true at the ORDER level
      only. Both sides did merge (hidden); a later post by either
      author would back both tips and render as a join. It is
      order-stable, not topologically un-reconcilable.
