# Measured 26/08/18-19

- scripts kept outside the repo (scratchpad, `--root` only)
- snapshots are QUADRATIC: one per commit, each serializing
  the whole `G`, so total ~= 0.25 * N^2 KB
- confirmed to N=10000 (grow.sh, one post per second):

| posts | states  | .git    | share | newest | build  |
|-------|---------|---------|-------|--------|--------|
|   100 | 2.7 MB  | 6.7 MB  |  40%  |  51 KB |    6 s |
|  1000 | 250 MB  | 283 MB  |  88%  | 0.5 MB |   74 s |
|  2000 | 996 MB  | 1.03 GB |  97%  | 1.0 MB |  173 s |
|  5000 | 6.2 GB  | 6.24 GB | 99.4% | 2.5 MB |  582 s |
| 10000 | 24.8 GB | 24.9 GB | 99.9% | 5.1 MB | 1648 s |

- per-snapshot cost exactly linear: ~0.5 KB per action
- LATENCY too, not only disk: each post writes a full
  snapshot (5 MB at 10k); posts slowed ~14/s -> ~6/s
- prune keeps W = min(fork.actions, actions in fork.time)
  snapshots <= 100, each ~0.5*N KB:
    -  1k actions: 250 MB ->  50 MB  (5x; W=100)
    -  5k actions: 6.2 GB -> 250 MB (25x)
    - 10k actions: 25 GB  -> 510 MB (49x)
    - slow chains keep fewer (time axis binds): better cut
- residual is O(W*N), still linear in N; constant space
  would need incremental snapshots (different design)

# Design: the boundary is authoritative (26/08/19)

- `C.prune.actions = 500` ACTIONS, flat constant
    - dominates the hardfork window, which is CAPPED at
      fork.actions=100 order entries: `low = #our-100+1`,
      the 7-day axis only settles a SMALLER suffix, never
      reaches deeper (sync.lua:14,32). So 500 >> 100 on any
      chain, fast or slow -> no rate dependence
    - the extra 400 is grace: how old a branch may attach
    - disk O(keep*N)
- BELOW the boundary every reader ERRORS, none recomputes:
    - abandon refuses (P1)
    - sync refuses (P2)
    - so pruned snapshots have NO reader; E0 stays dead

## Insight: deep attach is NOT a hardfork (26/08/19)

- a branch rooted below the window merges fine when
  consensus APPENDS it after the settled prefix
  (hardfork() only compares our[1..set])
- but its octopus is the old fork point, and sync.lua:127
  does STATE.read(oct): fatal on a pruned snapshot
- so "below the window is unreachable" was WRONG; the
  boundary must be enforced, not assumed

## Why error, not recompute (E0): DoS

- STATE.read(oct) runs BEFORE replay validates anything
- junk commit on an ancient base costs nothing, no reps
- each such sync would force replaying my whole history
  to rebuild the octopus state: O(N) amplification
- a different fork point per request defeats memoization
- with an error the attack collapses to a refused sync
- honest absentee beyond K rejoins as in the README:
  abandon -> recv -> repost (same escape as hardfork)

# P2 DONE (26/08/19): sync refuses a deep fork

- `C.prune.actions = 500` in constants.lua
- check lands in the recv branch, which the pre-receive
  hook also runs -> push AND pull gated in one place
- prune.lua green (P500 accept / P501 refuse); 12 sync
  tests unaffected (no over-refusal)

- BEFORE `STATE.read(oct)` (sync.lua:127): refuse if more
  than `keep` ACTIONS sit above the fork
    - `git log --diff-filter=A --format=%H HEAD ^oct
      -- actions/ | head -(keep+1) | wc -l`
    - error `chain sync : pruned state`
    - `head` caps the walk at keep+1 (only need "> keep?");
      wc is the last pipe stage so git's SIGPIPE exit is
      hidden -> exec sees wc's 0 (verify in a test)
- the check is a DEPTH rule, not `STATE.has(oct)`
    - `STATE.has` is sweep-local: A (swept) refuses, B (not
      swept) accepts and forms a merge rooted at the deep
      fork -> A then refuses B FOREVER, no reorder, no
      abandon escape (A lacks a snapshot, not bad history)
    - depth is protocol-visible: both peers compute the
      same count, both refuse, no merge forms, no split
- mechanic needs NO snapshot (the whole point):
    - `oct = octopus(loc, rem)` is pure git already
      (consensus.lua:10: rev-list --boundary + merge-base)
    - oct is an ancestor of loc=HEAD, so `HEAD ^oct` counts
      my commits above the fork = its depth from my tip
    - one subprocess, reads nothing
- prune safety is a CONSEQUENCE: pass the check => oct is
  within the last `keep` commits => its snapshot was never
  pruned. keep >= entrenchment window (see boundary)
- `keep` is an ACTION count (order entries), NOT commits
    - commit count is adversarially unsafe: merges are not
      bounded by actions, a peer can force many recvs, so
      100 actions could span > 500 commits -> prune deletes
      a snapshot entrenchment (100 actions) still needs
    - `--diff-filter=A -- actions/` counts adds only, so
      merges are excluded: exact action axis, one subprocess
- deep-attach loser case: `count HEAD ^F` with F deep is
  large > keep -> refused on both peers (was accepted
  today; that acceptance is what needs oct's snapshot)
- tolerant readers need no change:
    - `sync.lua:227` replay seeding just replays instead
    - `consensus.lua:232` writes what is missing
