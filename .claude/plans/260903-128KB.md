# Payload size limit (rule 4.c, 128 KB)

- spec'd, never enforced: `post.size = 131072` is commented out in
  `constants.lua`

# Why local, not consensus

- payloads are off the DAG: fetched after `main` is replayed, never
  seen by `apply`
- a post with missing bytes is already a valid state
- the value is never replayed: local policy, not genesis
- so 4.c means: each peer bounds what it STORES

# Design

- L1 post, and `like --why` (same anchor): refuse > size before
  hashing, `ERROR : chain post : payload too big`
    - stops honest clients only
- payload fetch by explicit cids (actions missing their bytes), no
  `refs/payloads/*`; keep a ref only if its target == the commit's
  blob, else delete
    - today any advertised ref is kept: junk under 128 KB,
      unbounded in count (sync.lua ln 262-305)
- L3 recv scan: size of each fetched payload; too big: drop the
  anchor, add the cid to an oversized list
- oversized list
    - fed into the negative refspecs, next to revoked: no refetch
    - skipped by the re-anchor loop (sync.lua ln 296-305), which
      would re-attach the blob until `sweep`
- `get payload` on missing bytes: `missing payload`, not a crash
  (get.lua ln 65)

# Limit

- an oversized payload still crosses the wire once: git 2.43 has no
  fetch-side size cap (TODO.md "Transfer caps")

# Order

- 1: constant + L1 (post.lua, like.lua)

# Won't do

- L2 fetch filter (+ wrapper tree, `allowFilter`, promisor cleanup)
    - only a request: a modified sender ignores it
    - honest peers never serve oversized payloads (L3)

      re-pulls the blob unless the promisor config is removed
- withholding tracker (needs 260722-peers)

# Rejected

- size in the commit message: trusts the poster
- genesis constant: not replayed, no reason to agree
