# Payload size limit (reps.md rule 4.c, 128 KB)

- spec'd since v0.8, never enforced: `constants.lua:32` has
  `post.size = 131072` commented out
- threats.md T6a still says "planned"; transfer.md covers
  the git-level knobs; done/280808-redesign.md demoted it:
  "a transport policy, not a tree concern"

# Why not a consensus rule

- payloads are OFF the DAG: a post commit names a blob
  hash, the bytes sit at `refs/payloads/<cid>`, fetched in
  a separate pass AFTER `main` is replayed
- replay never sees the bytes, so a size check in
  `ACTION.apply` can never run at recv time
- a post whose bytes are missing is ALREADY a valid state
  (`sync.lua` end-of-sync scan heals it next time)
- the value is never replayed -> LOCAL policy, not genesis
  (TODO.md "Per-chain constants" test: does it derive G?)
- so: rule 4.c becomes "each peer bounds what it STORES"

# Measured 26/09/03 (git 2.43, scratch repos)

- `fetch --filter=blob:limit=131072` on a ref that points
  DIRECTLY at a blob: the blob still lands (196 KB pack)
    - a ref tip is a WANTED object; filters prune only
      what traversal reaches
- same, ref -> annotated TAG -> blob: still lands
- same, ref -> TREE `{ p = blob }` -> blob: MISSING (1 KB)
  = the only shape the filter bites
- server without `uploadpack.allowFilter`: "filtering not
  recognized by server, ignoring", everything lands
- the filtered fetch AUTO-registers the URL as a promisor
  remote (`remote.<url>.promisor=true`), and any later
  `cat-file -e` on the missing blob LAZILY fetches it
    - `GIT_NO_LAZY_FETCH` is absent in 2.43
    - `config --remove-section remote.<url>` after the
      fetch stops it: the blob stays missing
- payloads are never PUSHED: `sync send` pushes only
  `main` + `refs/begs/*`, the hub's hook re-runs `recv`
  from the `url=` option -> ONE fetch path, hub included

# Design: three layers, all local

- L1 `post`: refuse `> C.post.size` before hashing
    - nobody publishes what peers will not fetch
    - `ERROR : chain post : payload too big : <n> > <max>`
- L2 recv fetch: `--filter=blob:limit=<size>` (bandwidth)
    - requires the wrapper tree (below) on the SENDER
    - requires `uploadpack.allowFilter true` at init
      (`chains.lua` config block), so v0.21 peers serve it
    - remove the auto promisor section right after
- L3 recv scan: `cat-file -s` per newly anchored blob
  (disk, and the fallback for a server that ignores L2)
    - too big: drop the anchor, never set it; sweep reaps
    - same loop as the revoked-anchor scan, one pass
- L0 hub: `receive.maxInputSize` on the push path
  (transfer.md); caps `main`+begs packs only; zero code

# Layout change: wrapper tree

- `refs/payloads/<cid>` -> tree `{ p = <blob> }`, not blob
- the commit message still names the BLOB hash: consensus
  bytes untouched, `get payload` still `cat-file blob`
- writers: `post.lua:88`, `like.lua:195,205` (LIFT/anchor)
- readers of the ref: `sync.lua` `has[]` scan (refname
  only, unchanged), `abandon.lua:112` (delete, unchanged)
- `cat-file -e <blob>` probes (`like.lua:166`, `sync.lua`)
  read the object db, not the ref: unchanged
- one tiny tree object per payload: negligible
- no back compat: v0.21 is pre-release (as member rename)

# Order

- 1: L1 + constant
- 2: wrapper tree (writers) + `allowFilter` at init
- 3: L3 scan in recv
- 4: L2 filter + promisor cleanup
- 5: docs

# Rejected

- consensus rule in `apply`: bytes absent at replay
- size in the commit message: trusts the poster
- tag wrapper: filter does not bite (measured)
- genesis constant: not replayed, no reason to agree
- fetch then drop ALONE: bytes already crossed the wire
