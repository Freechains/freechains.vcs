# CLI: Commands Missing Since v0.8

- Diff of `../README/docs/cmds.md` (v0.8) against `cli.md` (v0.20)
- Nothing decided yet: each item lists its open questions
- Ordered by cost, cheapest first

# Covered by rename (no work)

- `chains join | leave | list` -> `chains add | rem | dir`
- `chain consensus` -> `chain list order`
- `chain get block` -> `chain get metadata`
- `peer (send | recv) <chain>` -> `chain sync (recv | send)`
- `chain reps <hash_or_pub>` -> `chain reps action | author`
- `freechains-host start <dir>` -> `daemon --root=<dir>`

# Small ergonomics

- Three one-liners, no design questions
- `chain post -`
    - posts from standard input
    - today only `file <path>` and `inline <text>`
- `chain get (metadata | payload) <id> file <path>`
    - writes to a file instead of standard output
    - matters for binary payloads
- `chain heads` -> DONE as `list tips` (260901-list-tips.md)
    - the DAG tips, sorted bare cids, one per line
    - v0.8 `heads blocked` maps to `list begs`

# daemon stop  [x] DONE (done/260902-daemon.md)

- `daemon stop [--port]`: kills every holder of the port
  (children too); local only; no pid file

# chain genesis

- Prints the genesis message of the chain
- `refs/genesis` exists in every repo; the genesis is NOT an
  action, so `get metadata` does not cover it
- cheap: `git cat-file commit refs/genesis`, tail

# peer ping

- Round-trip time to a remote peer
- Open: what does it speak?
    - `git ls-remote` is the only handshake we have
    - a real ping needs a daemon-side verb we do not have
- Useful as a liveness check before `sync`

# peer chains

- Lists the chains a remote peer serves
- Open: `git daemon` exports directories, not a chain list
    - needs an endpoint, or a served index file
- Privacy: a hub may not want to enumerate its chains
    - v0.8 had no such notion
    - likely an opt-in daemon flag

# chains listen / chain listen

- Blocks and reports actions as they arrive
- The only v0.8 command with no analogue at all
- Open: what is the event source?
    - pushes land via `--hub`, so a git hook could fire it
    - `sync recv` is client-driven, nothing to hook
- Open: output format, one line per action or per batch?
- Open: does it survive a hard-fork refusal?

# keys

- v0.8 `keys (shared | pubpvt) <passphrase>`
- Deterministic key pair from a passphrase
- Today the user runs `ssh-keygen` by hand
- Open: can `ssh-keygen` be made deterministic?
    - not directly; would need our own ed25519 derivation
    - see `crypto.md` for the openssl/luasodium choice
- `shared` only makes sense with private chains, see below

# Private and identity chains

- The largest deletion from v0.8, a design area not a command
- Missing chain types
    - `$<name>`: private group, shared symmetric key
    - `@<pubkey>`: public identity, owner's key
    - `@!<pubkey>`: identity where only the owner posts
- Missing options
    - `--encrypt` on `post`
    - `--decrypt=<pvt>` on `get`
- Today all chains are the public kind (`/` aliases; open
  and dictator variants exist since v0.21)
- Open: does the reps model even apply to `$` and `@`?
    - `@!` has one author, so likes buy nothing
    - `$` members are already vetted by the shared key
- Open: encrypted payloads live outside the DAG already
    - so `revoke` and `sweep` may need no change
- Suggest: decide the WHY before any code
    - if reps are the point, `#` may be the only type we want
